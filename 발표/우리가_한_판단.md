# 우리가 한 판단 — 구체적인 예

"뭘 직접 했냐"는 질문에 **설계 철학으로 답하면 약합니다.** 걸렸던 문제와
어떻게 풀었는지를 말하면 그게 증거입니다.

아래는 전부 **실제로 있었던 일**이고, 숫자는 직접 잰 것입니다.
하나만 골라서 말해도 충분합니다.

---

## 1. 보드가 안 잡혔습니다 — 핀 하나 때문에

햅틱 보드를 꽂았는데 `DA7280 not found` 만 반복됐습니다. 케이블도 멀쩡하고
보드도 멀쩡했습니다.

I2C 를 훑는 진단 코드를 따로 짜서 돌렸더니, **보드에 내장된 배터리 잔량계(0x36)
까지 같이 사라지는** 게 보였습니다. 케이블 문제면 그건 안 사라집니다.

> 원인은 이 보드가 **Qwiic 포트 전원을 GPIO 7 로 따로 켠다**는 것이었습니다.
> 세 줄을 넣으니 바로 잡혔습니다.

```cpp
pinMode(PIN_I2C_POWER, OUTPUT);
digitalWrite(PIN_I2C_POWER, HIGH);
delay(100);
```

**왜 이게 우리 일인가** — 증상만 보면 케이블이나 납땜 문제로 보입니다.
포트에 전원이 따로 들어온다는 건 데이터시트를 읽고 실측해야 나옵니다.

---

## 2. 자막이 틀려서 실험이 무너질 뻔했습니다

실험 영상을 만들 때 Whisper 가 1번 클립 **"이제 안 와"** 를 **"이리자누아"** 로
받아썼습니다. 12번은 "뒀어"를 "있어"로.

자막이 틀리면 **'자막만' 조건이 통째로 무의미해집니다** — 참가자가 못 읽는 게
감정 때문인지 오타 때문인지 구분이 안 됩니다. 의도한 문장을 자막으로 넣었습니다.

**왜 이게 우리 일인가** — 모델 출력을 그대로 믿었으면 실험 결과 전체가
쓸모없어졌을 겁니다.

---

## 3. 모델이 12개 중 1개만 맞혔습니다

실험 영상을 만들기 전에 모델을 돌려 봤더니 **2~3초 클립에서 12개 중 1개(8%)**
만 맞혔습니다.

그대로 썼으면 '자막+SoundShape' 조건이 대부분 **틀린 감정**을 보여 주게 됩니다.
그러면 재려던 것(시각 언어가 전달되는가)을 못 잽니다.

> 그래서 **정답 감정을 직접 지정해서** 렌더했고, 보고서에 **이 실험은 인식
> 정확도가 아니라 시각 언어 전달력을 재는 것**이라고 못 박았습니다.

**왜 이게 우리 일인가** — 숫자가 안 나오는 걸 숨기지 않고, 실험이 무엇을
재는지 다시 정의한 겁니다.

---

## 4. 한국어가 안 돼서 임베딩을 갈아 끼웠습니다

공개 모델 그대로 한국어 **17.5%**. 7지선다에서 찍으면 14%입니다.

모델을 바꾸고 데이터를 바꿔 봐도 안 올랐습니다. 마지막으로 **목소리를 숫자로
바꾸는 부분(백본)만 바꿔 끼우며** 비교했고, 한국어 전용 임베딩에서 **49.6%** 가
나왔습니다.

**왜 이게 우리 일인가** — 어느 부품이 문제인지 알아내려면 하나씩 바꿔 가며
재야 합니다. 성능 향상의 대부분이 여기서 나왔습니다.

---

## 5. 다국어 모델이 한국어를 반대로 읽었습니다

글자 뜻을 보는 모델로 다국어 BERT 를 쓰고 있었는데, 한국어에서 **명백한 부정
문장을 긍정으로** 분류했습니다.

한국어만 한국어 전용 모델로 분기시켰습니다. 코드에 언어별 라우팅이 들어 있습니다.

**왜 이게 우리 일인가** — "다국어 모델"이라는 이름을 믿고 넘어갔으면 한국어
결과가 계속 틀렸을 겁니다.

---

## 6. 비꼼을 살리려고 조건을 걸었습니다

글자 뜻과 말투가 다를 때 말투를 믿게 했는데, **항상 그러면** 평범한 긍정문까지
비꼼이 됩니다.

그래서 **말투의 긍부정이 ±0.2 안쪽일 때만** 글자를 참고하도록 했습니다.
말투가 확실하면 글자는 아예 안 봅니다.

```python
if abs(acoustic_v) >= VALENCE_UNCERTAIN_BAND:
    return acoustic_v   # 말투가 확실하다 → 글자 무시 (비꼼 보호)
```

**왜 이게 우리 일인가** — 규칙 하나를 넣는 건 쉽고, **언제 적용할지 정하는 게**
어렵습니다.

---

## 7. 재학습이 25분 걸리던 걸 3.5초로

시청자 답변으로 재학습하는 기능을 만들었는데, 학습이 **25분 넘게** 걸리고
끝나지 않았습니다.

원인을 따라가 보니 **피드백이 결정 경계 근처에 몰려 있어서**였습니다. 확신이
낮을 때만 물어보니까, 모인 답들이 전부 애매한 구간의 표본이고, 그걸 가중치까지
줘서 넣으면 수렴이 극도로 느려집니다.

> 반복 횟수에 상한을 두는 것으로 **3.5초**가 됐습니다. 약간 덜 수렴한 모델이
> 영원히 안 끝나는 것보다 낫습니다.

**왜 이게 우리 일인가** — 느린 이유가 **기능 설계에서 나온 구조적 문제**라는
걸 알아야 고칠 수 있습니다.

---

## 8. 성능이 떨어지면 모델 교체를 거부합니다

재학습한 모델이 **기존 데이터에서 성능이 떨어지면 설치하지 않습니다.**
새 데이터에서 개선이 없어도 거부합니다.

```python
if gain <= 0:                      return False, "도메인 개선 없음"
if drop > MAX_BASE_REGRESSION:     return False, "기존 성능 하락 초과"
```

**왜 이게 우리 일인가** — "사용자 피드백으로 좋아집니다"는 말은 쉽지만,
**나빠질 때 막는 장치**가 없으면 그냥 위험한 기능입니다.

---

## 9. 잘 되는 기능을 껐습니다

화자가 바뀌면 자막에 `-` 를 붙이는 기능을 만들었습니다. 판별 성능은
**AUC 0.958** 로 잘 나왔습니다.

그런데 **끝까지 검증할 수가 없었습니다.** 실험 데이터셋에 문장이 두 개뿐이라
대화를 만들면 Whisper 가 반복으로 보고 40~44% 를 버립니다.

> **껐습니다.** 설정 파일에 이유를 적어 두고 `enabled: false` 로 뒀습니다.

**왜 이게 우리 일인가** — 숫자가 좋다고 켜는 게 아니라, **쓸 수 있는지 확인될
때까지 끄는** 판단입니다.

---

## 10. 이름을 붙이는 대신 작대기를 골랐습니다

화자 구분을 만들 때, 처음엔 "민수: …" 처럼 **이름을 붙이는** 방식을 생각했습니다.
그러려면 영상 전체에서 **몇 명인지 모르는 채로 목소리를 묶어야** 합니다. 틀리면
시청자 눈에 바로 보입니다.

방송 자막은 화자가 바뀔 때 앞에 `-` 를 붙입니다. 이건 **"앞 사람과 다르다"** 만
주장하면 되므로, **바로 앞 구간과만 비교하면** 됩니다.

> 규칙을 바꾸니 어려운 문제가 쉬운 문제가 됐습니다. 그래서 이 모듈에는 **묶는
> 코드가 한 줄도 없습니다.**

**왜 이게 우리 일인가** — 알고리즘을 고른 게 아니라 **문제를 다시 정의한** 겁니다.

---

## 11. 음악이 없으면 분리를 건너뜁니다

목소리 분리는 무겁습니다. 그런데 사람들이 올리는 영상 대부분은 **배경음악이
아예 없습니다.**

**앞부분만 먼저 분리해서 재 보고**, 음악 에너지가 기준 아래면 나머지는 건너뜁니다.

**왜 이게 우리 일인가** — 음악이 있는 영상에서는 비용이 그대로이고, 없는
영상에서는 거의 공짜가 됩니다.

---

## 12. 손목은 세기로 구분이 안 됐습니다

밴드가 보낼 수 있는 건 세기 하나뿐입니다. 만들어 놓고 차 보니 **분노와 기쁨이
똑같이 느껴졌습니다** — 둘 다 각성도가 높아서 똑같이 세게 울립니다.

세기를 **시간으로 펼쳤습니다.** 분노는 짧게 세 번(주기 0.78초), 슬픔은 느리게
부풀었다 꺼집니다(2.28초). 손목은 세기보다 **간격**을 훨씬 잘 가릅니다.

**왜 이게 우리 일인가** — 채널이 하나뿐이라는 제약을 **시간 축으로 우회한** 겁니다.

---

## 13. 말이 끝났는데 손목이 계속 떨렸습니다

자막 길이만큼 진동시켰더니 말이 끝나고도 계속 떨었습니다. 재 보니 어떤 줄은
**자막 9.0초, 실제 발화 1.8초** 였습니다. 장면이 이어지니 자막은 떠 있는 게
맞지만, 손목은 아닙니다.

소리 크기로 막아 보려 했는데 안 됐습니다. **대사가 끝난 구간의 배경음(0.19)과
가장 조용한 대사(0.33)의 범위가 겹칩니다.** 문턱을 격자로 다 돌려 봐도 대사를
놓치지 않으면서 누수를 32% 아래로 못 내립니다.

> 그래서 **파이프라인이 내준 발화 길이**를 쓰기로 했습니다. 추측할 필요가 없는
> 값이 이미 있었습니다.

**왜 이게 우리 일인가** — 안 되는 접근을 **측정해서 포기한** 다음, 이미 가지고
있던 정보를 쓴 겁니다.

---

## 14. 확신도 기준을 숫자로 정당화했습니다

"확신이 낮으면 흐리게"의 기준을 45% 로 뒀는데, **왜 45% 인지** 답할 수 있어야
했습니다.

재 봤습니다. 확신 **45% 이상 구간은 73.6%** 정확하고, **미만은 39.1%** 입니다.
흐려지는 구간이 실제로 두 배 가까이 더 틀립니다.

**왜 이게 우리 일인가** — 임의로 고른 숫자와 **데이터로 고른 숫자**는 다릅니다.

---

# 어떻게 쓸 것인가

심사위원이 "직접 했냐"고 물으면 **하나만** 고르십시오. 전부 말하면 변명처럼 들립니다.

| 상황 | 고를 것 |
|---|---|
| 기술을 파고드는 심사위원 | **4번** (임베딩 교체) 또는 **7번** (수렴 문제) |
| 설계를 보는 심사위원 | **10번** (문제 재정의) 또는 **6번** (비꼼 조건) |
| 태도를 보는 심사위원 | **9번** (잘 되는데 껐다) 또는 **3번** (8% 를 숨기지 않았다) |
| 하드웨어를 물으면 | **1번** (GPIO 7) 또는 **12번** (리듬) |

**9번이 가장 셉니다.** 성능이 잘 나온 기능을 검증이 안 돼서 껐다는 건,
숫자를 꾸미지 않았다는 증거입니다.
